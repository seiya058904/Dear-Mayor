# V5 / V6 首装与恢复性能对照（本地测量）

日期：2026-10-20，北京时间。没有为本轮性能研究修改 Service Worker、资源、字体或主包结构。**没有证据支持宣称 V6 首屏加速。**

## 环境与定义

- win32 10.0.22631；AMD Ryzen 7 9700X 8-Core Processor             ；Node v24.15.0；Playwright Chromium 156.0.8078.4。同一个依赖安装和构建工具链。
- V5 是指定干净提交 `39fda12e86b52084db36654e9311105a8ae4b367` 修改前的生产 build，保留在 `.local/v5-dist/`；V6 为本地 `dist/`。两版文件清单与 SHA-256 见 [builds.json](v6-evidence/builds.json)。
- 每版 × 桌面 1920×1080 / 模拟安卓 390×844 × 未限速 / 慢网，各取一个冷样本，共 8 个；固定顺序 V5 再 V6。每个使用独立空 browser context，无 HTTP/SW 缓存和存档。不是交错多轮统计实验，几十毫秒差异不能解释为收益。
- 移动配置：isMobile、触摸、DPR 2.75 和安卓 UA；**模拟而非实体安卓**。慢速配置用 CDP 对页面施加 4× CPU；服务器对所有响应（含 SW）施加共享名义上限 200000 bytes/s（1.6 Mbps）、150 ms 首响应延迟，50 ms 一个 10000-byte 预算，实际吞吐见下方校准限制。FIFO 响应队列、全 MIME gzip、Cache-Control: no-cache、无 ETag；这是一种保守可重复模型，不等同真实浏览器的网络优先级，也不代表 GitHub Pages 实际缓存/延迟。
- 文书 DOM：观察到 article 与 decision 的 performance.now；可选择：等待可见 article 后真实点击批准，立即验证持久化 history 已前进一步；不是仅查按钮存在。FCP 来自 Paint Timing。字体：第一份文书 DOM 出现后 await document.fonts.ready 的时点；避免在尚无正文时过早读到已 resolved 的空字体集合。
- 离线准备：SW ready 且 controller 已接管，安装 cache.addAll 已完成；之后列出全部缓存条目和 decoded 字节。实际传输按本地服务器响应编码后的 body 和 HTTP header 计数，覆盖主页面和 worker 请求；不是磁盘体积估算，未包含 TCP/TLS 开销。
- 恢复：由真实引擎生成同 seed、批准路径的合法 0/100/860 次决定存档，V5 固定目录 20、V6 固定 21；写入隔离 localStorage，再测三次已有 SW 缓存的整页 reload 至目标可见。时间包含读取/历史重放/缓存加载/渲染，未伪称纯 engine restore。三次原值在 JSON，表中用中位数。
- 内存：在各存档恢复后显式 GC，取 CDP JSHeapUsedSize。仅为 JavaScript heap 随历史长度的快照，不包含图片解码、GPU 或完整浏览器进程，也不是连续 860 次真人点击的内存泄漏测试。
- 所有 profile 最后断网重载 860 次存档，并真实点击搁置验证 history=861；不以 SW ready 信号单独替代离线实测。

## 冷首装结果

测量修正记录：首轮未限速的四次点击早于 FCP，已丢弃并在等待 FCP 及两帧后重测；四个保留慢网样本的 FCP 均早于点击。原轮与重测日志留在 `.local/v6-evidence/`，最终 JSON 每行注明采用哪一轮。

网络校准限制：200000 bytes/s 是每 50 ms 定时预算的**名义上限**。此 Windows 主机实际计时与调度下，完整冷加载平均 body 吞吐约 **159～160 kB/s（约 1.28 Mbps）**，没有达到持续 1.6 Mbps。以下时间应连同这个实测吞吐阅读；理论字节换算仍用名义上限，不是标准网络整形器的 1.6 Mbps 测试结果。

## 不适用当前设备的预缓存

两版完整缓存均为 22 个条目，包括 root/index 两个入口。以下项目在每种视口的实际 CacheStorage 清单中都存在；首装网络日志同样有传输，而不是只静态阅读 sw.js 推断。当前未打开批示便已经取到 note。

| 当前设备 | 可稍后才需用的资源 | 测量服务器 gzip bytes | 1.6 Mbps 理论传输时间 |
|---|---|---:|---:|
| 桌面 | background.webp, paper-mobile.webp | 3,030,381 | 15.15 s |
| 手机模拟 | background-wide.webp, paper.webp | 3,051,028 | 15.26 s |
| 两者，未开批示 | note.webp | 1,307,836 | 6.54 s |

这些并非都可删除：改变窗口宽度可能需要另一张纸与背景；批示要用 note，完整离线应保留这些能力。字体原文件 5305668 bytes，宽幅背景 1886514 bytes，均未改变。

## 后续低风险方案（只研究，未实现）

1. **先确定生产是否重复传输，再复用同版本已完成响应。** 本地 no-cache 模型中，首屏与 cache.addAll 对同一 URL 的请求会重复送 body；生产 HTTP 缓存可能已消除一部分。未来可在完整 build 内容校验下研究复用本次首屏资源或浏览器缓存，最终 CacheStorage 仍需全部 22 个条目且通过根/子路径、升级和离线测试。不能无版本验证地复用旧背景/脚本。
2. **资源分批且保持同一个完整离线完成条件。** 先处理本视口和批示必需文件，再处理另一视口的纸/背景；只有全部成功才认定完整离线。桌面可延后约 3.03 MB（约 15.15 s），手机约 3.05 MB（约 15.26 s）的当前不用资源，但它们只是移到后面，**完整离线总字节不会因此减少**。若还延后 note，必须在完整离线宣告前补齐，不可让断网后批示丢图。当前 SW 在 window load 后注册，单靠重排预缓存不应宣称能加速首次文书。
3. **收益估计必须带上界。** 在此服务器编码下，V6 完整 22 项约 14.19 MB，单凭 1.6 Mbps 就需约 70.95 s（还没算首屏其他重复、延迟、解析）。复用本次已下载资源理论上最多省掉这些重复响应的编码 body；下表只是当前测量的可研究上界，未实施、未验证，不是已获得收益。不能为了消除 bundle warning 拆开目录并破坏旧档回放。

完整原始样本、请求逐项字节、CacheStorage decoded 大小、三次恢复原值与 heap 快照见 [performance.json](v6-evidence/performance.json)。复现：先从指定 Git 基线构建并保留 `.local/v5-dist/`，再构建候选，停止其他功能测试，运行 `npx tsx scripts/v6-performance.ts`（需要空闲的本地 52742、52743 端口；8 个 profile，慢网部分约十分钟）。不会修改游戏、依赖、生产配置或真实玩家存档。
