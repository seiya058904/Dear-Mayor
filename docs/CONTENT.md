# 内容与规则扩展

## 已实现的边界

`chains-a.ts`、`chains-b.ts`、`chains-c.ts` 各有四条故事线。每条包含 `start`、四个互斥 `branches`、`continuation`、`finale`。总共 84 个故事节点。`daily.ts` 另有 32 封独立日常信。单局每条链只会进入一个分支，故 12×4+32 = 80 封。循环日常是维持内容耗尽后的可操作性，不计为新增原创档案。

每个文书由 `author.letter` 规范成标题、段落、署名、三项回复与三个普通决策后果。文字必须提出明确请求；不要让批准变成无意义的下一页按钮。

## 添加与修改

1. 给故事线一个稳定英文 ID；为人物写稳定口吻。不要改动已发版 ID 的含义。
2. 起始信写一个具体请求，通常 80～220 汉字。首封原文是视觉基线，应保留。
3. 分别写批准、正式拒绝、无答复、批示后的不同信件，不把沉默写成禁令。批示正文会引用具体选择的结果。
4. 为后续和收尾各写新的请求。渲染时正文首段引用同一故事线上一阶段的实际结果，文内不可自行断言另一条分支已发生。
5. 每封配置三项贴题的回复及各自结果。独立日常信也有三种不同处理建议，不能用四个通用选项塞满内容。
6. 添加后更新数量断言与 README，并执行全部检查。对重点故事做真实浏览器连续阅读。

## 调度与隐藏状态

新局种子固定为 6271，便于复现；测试覆盖其他种子。每天最多引入一位新的故事线发信者；到期后续优先安排，其余空位由尚未读过的日常信填充。处理四封后换日，后续最早相隔两日。没有合适来信时日期推进到下一次到信，不重放旧信填数。

状态包括日期、日内位置、当前信、种子、处理历史、待送信件、已开始故事线、已选日常信与各线最近结果。这里没有数值经济模拟；世界记忆由分支与文本后果构成。所有这些内部记录都不作为玩家面板展示。

`decide(state, expectedId, action, reply?)` 返回新状态。过期 ID、已处理 ID 与无效选项不产生变化。UI 同时同步锁住提交，先保存再播放离场，以防刷新或双击复制操作。

## 存档兼容

存档键为 `dear-mayor:save:v1`。加载时从种子和合法历史回放，重新计算队列与事实；不能读取的存档尝试复制到 `dear-mayor:save:v1:recovery`，保留原件直到玩家继续操作。首次新局默认不覆盖旧坏档。

已有 ID 的后果文字与调度顺序属于 v1 回放契约。修改它们会影响旧存档校验；需要加明确迁移或升级存档版本，不能悄悄让老玩家跳信。新增内容也应考虑队列兼容。代码已实现安全恢复，但没有为尚不存在的未来版本预造迁移规则。

## 当前迭代空间

- 12 条主要链在第二阶段分流、后两阶段汇合，保留上一阶段结果；不是每个选择都生成一条永久独立的故事树。
- 32 封日常短函主要用于镇民生活变化，不各自拥有四阶段事件链。
- 主体结束后的四类循环函会重复主题，仅变换日期、轮次语境与前次记忆；后续可增加新的手写剧情季。
- 没有音效、跨设备存档、存档导入导出或在线模型。声效并非本次任务前提。
